Rust所有权机制
**************

基本原理
========

本文对Rust的所有权机制做一个概念建模。

Rust的所有权机制主要目的是避免UAF（Use After Free），避免使用非法指针。它的基
础还是“如果内存对象有引用，内存就不能释放”。为此，它把C的“分配内存”，变成了普
通变量的“被引用对象”。

怎么说呢？我们看个例子：::

  // 例1
  let a = String::from("hello");
  let b = a;

这里我们定义了一个变量a，背后有一个隐含分配，就是字符串"hello"，所以a是"hello"
（的所有者）的引用，但a并不是C语言的指针，它包括描绘这个字符串的所有元数据
（meta data），比如，就这个String来说，它还包含字符串的长度。

当我们进行赋值的时候，我们传递的是整个元数据，比如这里的b，它占据的空间包括指
向"hello"的指针和"hello"的长度。这个赋值，是所有meta data的拷贝。

所以，a的地位有点像C语言的指针，但它不是，它包括所有的meta data。关键是rust允
许类似C指针的另一个概念：引用。比如上面这个代码，也可以这样写：::

  // 例2
  let a = String::from("hello");
  let b = &a;

这里的b就更像指针，因为它用起来是一个指向a的meta data的一个指针。

所以我们没法简单用C的概念来说明rust的对应概念，你只能记得：rust的值，可以包含
需要为其生命周期负责的被引用对象。这种对象，部分教材总结为“堆数据”，这样抽象其
实没有抓住根本，真正的根本是：这是绑定这个对象的全局资源，可以是堆内存，共享内
存，IO资源等等。比如这里String::from("hello")分配的内存，是底层（非安全）库用
malloc一类的方法分配的，rust并没有free函数让你释放这个内存，rust是把这个资源绑
定给a，在a释放的时候自动释放这个资源的（称为drop）。

你完全可以用非安全代码实现一个XXDev::from(...)，生成一个设备对象，在这个设备
drop的时候，释放对应的设备资源。所以，这里的本质是，这个资源是全局的（当然，堆
是一种最常见的全局资源），但现在寄生在这个对象上面的，我把它称为
**被绑定资源**\ 。

**被绑定资源**\ 必须有一个而且是唯一一个“宿主”，以保证它一定不会丢失，而且有宿
主的时候一定不会释放，这是所有权机制的核心。在例1中，当a被赋值给b了，那么它的
**被绑定资源**\ 就迁移给b了，a就不能用了。这是改变\ **被绑定资源**\ 生命周期的
方法。

这一点单独看赋值看不出来，我们换一个例子：::

  // 例3
  let a = String::from("hello");
  let b = foo(a);

你调用另一个模块的方法foo，把a送给它，a绑定的资源的生命周期就转到foo内部了，而
foo内部的资源，也可以通过返回值，送回到你这个模块中，转化成你的资源。

所以，被绑定资源的可以通过传递的方式，被绑定它的那个变量的生命周期绑定。这个设
计让你无论有没有\ **被绑定资源**\ ，值都可以用赋值的方式传递。你赋值一个没有绑
定资源的结构{1, 2}或者原始变量，和赋值一个有绑定资源的结构，感官上是一样的，内
容全部都到了新的变量或者被调用的函数里面去了。

.. note::

  rust有另外一套Copy/Move的逻辑，如果一个对象被定义成Copy的，那么我们就认为它
  不带有被绑定资源，这样赋值后，原来的对象不会失效。很多人会用这个去解释这个所
  有权转移的逻辑，但我这里是在建模，是在抓核心要点，我认为这个不是核心要点，而
  是实现的妥协，所以这里不把这个逻辑放上主线。

那么引用呢？引用靠编译时检查。

rust不允许引用的生命周期比被引用的对象长。比如前面例2中，b的生命周期就不能比a
长。比如这个程序写成这样就是错的：::

  // 例4
  let b;
  {
    let a = String::from("hello");
    b = &a;
  }
  // println!("{}", *b); 如果写这句就会出错，因为b的生命周期比a长

这里a的生命周期只在大括号之内，而b在外面还能存活，如果继续使用，就报错了。

就这样看其实看不出这个规则的重要性，我们稍微调整一下：::

  // 例5
  let b;
  {
    let a = String::from("hello");
    b = foo(&a);
  }
  ...

我们平时写程序，就是这样把自己的引用转交其他模块的，你不知道foo会不会留着a的引
用，如果留着，a被放弃的时候，我们再调用foo的函数，就会出现UAF。

但如果不允许留着，那么我们就很难设计关联关系了。比如说，我们要把一个对象注册给
一个通知模块，我自己手上还有这个对象，对方在特定时刻要通知我，他需要有我的对象
的引用，这种情况就是仅仅支持值传递没法解决的问题。

所以，必须有个办法，把a的生命周期传递到函数内部去，让函数实现的时候可以比较引
用和输入参数的生命周期。先看最常见的例子，这个例子和模块内部的数据结构无关，只
和foo的接口有关。假定我们返回的b就是用a制造出来的，我们这样声明foo的签名：::

  fn foo<'a>(a: &'a String) -> &'a String;

这个形式呈现出来是一个泛型，泛型的参数不是类型，而是一个所谓“生命周期参数”，'a。
这个参数表示：“存在一个作用域'a，使a和输出都有效”。

这是rust的生命周期检查器的规则，从程序员的角度很难理解。程序员角度更容易的理解
是：返回值的生命周期不能超过参数a。

为什么呢？因为函数被调用的时候，形参a会有一个被a这个实例定义的生命周期L，如果'a
存在，'a必然是L的子集，从而可以推出：输出也必须是L的子集。所以，返回值的生命周
期也不可能超过L，也就是b不能活得比a长，否则违反检查规则。

上面这个例子比较简单，我们返回的就是个引用，如果我们返回的是个对象，那么这个要
求就要贯彻到对象里面去了：::

  // 例6
  struct B<'a> { str_ref: &'a String, }
  fn foo<'b>(a: &'b String) -> B<'b>;  // 'b写成'a也没有问题，两个泛型是互相独立的

foo返回的是个对象，但这个对象里面有个域要引用a，那我们在foo这个层次就应该看到，
返回的B不能活得比a长，而到了B里面，我们又说，如果B的生命周期不能比str_ref引用
的那个对象长，最终的结果就是返回的B生命周期不会比a参数更长了。

无论如何复杂的定义，它的逻辑就是：你有个值a，这个值引用了其他值b，那么a就不能
活得比b长。这样你可以放心地使用a，只要你能编译得过，a的每个成员都是可用的。

让我们总结一下这里的整个（单线程）的编程逻辑（我这里说的都是safe接口的，unsafe
的代码就和C一样了，那个当C理解就是了）：

* 首先，没有指针和单独的全局分配方案了，任何时候你要分配全局资源，都应该用封装
  好的对象，用这个对象的生命周期来控制那个全局资源的生命周期。

* 你不能做无类型的裸内存处理了，一个对象是什么类型的，就当作那种类型处理，如果
  非要强行切换，那就回到unsafe层去自己保护逻辑自洽。

* 模块间默认考虑你传递的是“值”，你是把元数据和被引用资源一起传递过去的。控制权
  整体交给那个模块。轻易别用引用，这样就不会UAF了。

从这个角度来说，在rust中，你不会UAF的核心原因：编译器一开始就不允许你的引用生
命周期比本体长。这其实大大削弱表达能力了，因为编译器是静态的，它杜绝的是所有可
能性，但我们平时写C代码，是靠动态顺序来保证不会UAF的：你建立一个结构，挂到另一
个模块的链表上，那个模块解链后调用你的函数，让你释放这个结构。这也不会UAF，而
rust要求链接你的结构的那个对象生命周期比你的结构短。这怎么比较呢？

当然，rust是有其他路子去解决这个问题的，但那已经在绕了，那不是它擅长的部分，我
们优先发挥它的优势方面，这个优势方面就是：你的逻辑要给谁，就是整个数据（值），
全部给它，让它自己搞定，它不建议你建立很多完全平等的互相引用的模块，因为这种结
构本身就是引起UAF的原因。

mut
===

mut的引入主要是解决一个这样的程序定义需要：我要修改的时候，其他人都不要修改，
也不要看。对rust，这也是一个编译期检查。它能给你的代码造成一个效果：如果你拿到
一个mut引用，那么现在你是独占的，其他人手上一定没有你的引用了。

所以它更大的作用不是声明这个变量的内容能否修改，而是你现在手上拿着的是否是唯一
的引用。实际上，即使你的变量不是mut，你完全可以调用它的方法修改它的内容，只要
这个变量的定义允许，你就可以改，并不受mut控制。

后面将会提到的Cell<T>就是个典型的例子。Cell把T封装在自己内部，即使你只有这个
Cell的只读引用，你也可以用Cell::set()去修改里面的内容。mut在设计思路上说，关心
的是不是你能不能修改它，而是如果你修改它，你得知道别人能不能修改。只读的T不允
许你一个个修改T的值，因为有可能不一样，而Cell::set()允许你一次修改整个值，因为
对于单一的线程，这是完整的一次变更。这个语法在帮你构造这样一种设计意图。

这个设计有挺多的细节的。考虑如下代码：::

  // 例7
  let mut a = String::from("hello");
  let b = &a;

我们这里有两个名字，a和b，都可以引用那个内容是"hello"的String。两者当然是不同
的，一个表示那个String的本体，一个表示对那个本体的引用。这看起来我们可能在可能
被读的时候同时具有修改的权限。其实不然，这个代码允许这样写，但在b存活的时候，a
是不能被修改的，所以，到头来，我们仍保证只有一个拥有者。

另一个细节是，我们怎么算b这个引用结束了？比如我们这样写：::

  // 例8
  let mut a = String::from("hello");
  let b = &a;
  let c = &mut a;     // 这句是错的!!!

因为b还没有退出作用域，我们认为它还有效，这时c就不是独占引用，编译器不允许。有
两个办法解决这个问题：::

  // 例9
  let mut a = String::from("hello");
  let b = &a;
  drop(b);            // 或者*b;
  let c = &mut a;

你drop掉b或者使用一次b，后面就可以抢这个引用，b只要被用过，它的生命就可以在被
抢权的时候结束。

这个mut的控制常常被函数接口用来限制调用方法，比如：::

  fn foo<T>(a: &mut T) -> String {...}

你调用foo，就要保证收回所有a的引用，这样foo修改a，包括访问它占用的全局资源，就
是安全的。如果a是self，那就意味着，foo所属的对象现在是独占的，也是很多对象控制
自己的引用数量的方法：你能调用这个方法，就意味这对象现在只有调用者这一个引用。


绕
==

前面说了，rust在编译期做了最大的限制，其他问题基本上都只能在这个语法基础上绕。
而整个所有权转移的机制其实是依赖单线程的，因为跨了线程，线程之间就没有共同的生
命周期判定逻辑了，更不可能静态判定谁活得比谁长了。

.. note::

   和前面讨论Copy Trait一样，我们这里是尝试抓住语言的核心逻辑，尽量不被具体实
   现影响我们的方向性判断，所以，这里我们不深入std::thread:scope，Send/Sync
   Trait这些概念引入的判断。scope可以通过“绕”的设计在几个线程间维护某种存活的
   生命周期，具有Send/Sync特性也会影响线程间传递所有权的判断，但这些不被认为是
   语言本身的基础逻辑。

所以这个所有权的判定，都是一个线程之内的。跨线程就只能在各自的线程中计算了。如
果线程间有共享变量，就只能包装在unsafe中管理了。所以就会有已经包装好的Arc<T>和
Rc<T>对象了：你原来有一个结构T，现在你要让两个线程共享，那我们把T放到堆上，本
地的那些变量就变成了Arc或者Rc。这两者都是Reference Counter，引用计数，引用计数
为0的时候就自动释放。其中Arc是Atomic RC，计数器是个原子变量，可以被多线程访问。
Rc的引用计数是普通变量，没有多线程安全。

.. note::

  提到Rc/Arc<T>，一般还会提到Weak<T>，但这只是这两者的“自然推广”主题，表示一个
  不影响Rc/Arc引用记数的引用，可以upgrade为强引用（就是Rc/Arc），也可以从强引
  用downgrade。这样的特性，在决定了多线程共享是这种思路以后，总会根据需求扩展
  出来的。

我说这是绕，这你很明显能看出来，它其实就是把解决不了的问题包装到unsafe世界中，
这些不是它原始语法的支持方法。从这里就能看出这个语言不是普适的方案，只是适合它
的场景的，它可以包装出一个安全的空间来而已。

所以，如果你要创建和新线程共享一个数据结构，你要这样写：::

  // 例10
  let foo = Arc::new(Foo::new("myfoo"));
  let foo1 = foo.clone();
  std::thread::spawn(move || {
        foo1.do_sth();
  });

这里我们有了两个对myfoo这个本地的引用：foo和foo1，foo留在主线程上，foo1被送到
子线程中。然后我们才能用它，这个语法已经比较难看了。但其实应用中情况会更恶劣：
Arc是原子的，这只是说计算引用计数的时候是原子的，但我们没有说Foo是原子的啊，所
以如果你两个线程都在访问这个Foo，那还是线程不安全的，所以这个代码其实要这样
写：::

  // 例11
  let foo = Arc::new(Mutex::new(Foo::new("myfoo")));
  let foo1 = foo.clone();
  std::thread::spawn(move || {
        foo1.lock().unwrap().do_sth();
  });

反正，你多一个功能，就会多一层包装，虽然很多包装拆解是编译态完成的，但这还是在
“绕”。

这些绕，背后常常就是把原来的变量，变成另一个变量的\ **被绑定资源**\ 。比如前面
这个Arc/Rc，如果不包装，我们直接就定义Foo，Foo带了自己的\ **被绑定资源**\ 我们
用定义出来的foo使用。foo在当前上下文的栈上，被上下文定义生命周期。现在我们把它
放在Rc里面，变成Rc<Foo>，那么，它的生命周期就被Rc决定了，那就是另一套协议了。
虽然它在尽量贴合rust的文化，但现在Rc被释放了，它也一定会被释放，而是等到所有指
向它的Rc都释放了，才会被释放。

另一个例子是Cell和RefCell。我们一般变量要满足借用规则，变成这种包装对象的一部
分后，规则就变成这些对象定了。比如：::

  // 例12
  let a = Cell::new(10);
  let b = &a;
  a.set(11);
  b.set(12);
  assert_eq!(a.get(), 12);

这里a是只读的，但a里面包装的10i32是由Cell来决定的，Cell允许你作为一个整体修改
这个值，规则就是Cell的实现决定的。

同样有RefCell：::

  // 例13
  let a = RefCell::new(10);
  let b = &a;
  {
   let mut val = a.borrow_mut();
   *val += 1;
  }
  let val = b.borrow();
  assert_eq!(*val, 11);

a也仅仅是个只读的变量，但RefCell的规则是运行时有一个实例可以借出它的可写对象，
这样它就变成一个用动态方法提供rust静态检查规则的对象了。一旦它给你产出了一个本
地的变量（你管不了它怎么产生这个变量的，因为封装中可以在堆里随便分配资源的），
比如这里的val，那么val自己，就开始完全遵循基础语言那套保护逻辑了。

但一旦你把静态的判断变成了动态的，运行期报错就成为不可避免的可能性，你该出错还
是会出错的，rust并不能让你的程序死不掉，只能让你死掉的位置是确定的，而不UAF那
样，甚至你都不一定知道错了。

所以还是那句话，rust的核心语法是不足以展现硬件的全部能力的，也不足以取代C的，
但它构造了一个“安全空间”，让你在这个安全空间中，只能做特定范围中的操作，从而保
证这个空间中的安全。如果你需要这个空间之外的能力，其实是靠unsafe的类C代码去保
底的。
