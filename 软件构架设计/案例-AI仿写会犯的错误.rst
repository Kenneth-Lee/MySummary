案例-AI仿写会犯的错误
*********************

这个文档延续\ :doc:`案例-有构架地解决问题`\ 的案例记录，但重点记录的是“仿写”类
型的错误。

前面那个案例很多都来自我把一个底层通讯库（libgqm）适配到redis中发现的，最近那
个工作告一段落了，我现在在把libgqm适配到gRPC库中，但以我在redis和libzmq上的经
验，直接适配RPC库是没有前途的，因为libgqm化简很很多基于polling的通讯库的底层，
直接适配只会背上更多包袱。所以，我是直接基于使用接口实现了一个新的库，gqmRPC。

所以，这里的例子和之前的例子不同，这不是AI直接设计带来的问题，而是它直接“抄”会
带来什么问题。

我们还是用我对它的反馈来看这些错误：::

  我一开始就觉得这个设计做得不好，改到这个版本，我才意识到原因——它的基础建模就
  是有问题的。让我给你分析一下：我们有三个需求：

  1. metadata怎么承载
  2. 对方不响应怎么办
  3. StatusCode的编码

  第三个是最简单的，这个你的设计没有问题，我们不讨论。metadata承载这个问题，
  gRPC是承载在http协议上的，所以它很容易加key-value对，字符串对字符串，因为这
  是协议本身的功能，未来要增加新的属性，也很容易。但我们现在是个二进制编码，那
  么如何编码，未来如何增加新的属性，这就需要一个长远的设计，但你跳过了这个考量，
  直接就写了几个域，就决定去实施了。这就是这个设计让人不舒服的地方，因为它就解
  决眼前的问题，完全没有从基础上考量这个问题。

  对方不响应这个问题也一样，这个问题的控制要素不是泛泛的放弃语义，而是用户会怎
  么使用这个接口，整个难度都在这里：到底是用户call的时候超时了，我们决定cancel，
  还是用户执行一个一步调用，然后wait超时，然后我们调用cancel？你决定了这个应用
  场景，我们开始思考：他要cancel，我们的node在什么状态？我能直接调用libgqm的接
  口cancel这个调用吗？可以直接释放这个调用吗？有什么接口可以用？这样的设计就是
  顺理成章的，但你现在直接讨论什么DrainPool，abandon-report，这好像在发明问题
  出来解决，而不是针对问题去寻找解决方案。

这个意思很直接了，我就不解释了，我们看下一个：::

   你的两个基础建模，第二个我赞同，第一个我有不同意见。gRPC引入metadata，是因
   为http本来就具有这样的特性，它有新功能要做了，就自然用了这个能力了。如果我
   们完全去仿造，反而引入了自己的短板，metadata本质上不就是为了传递一些协议层
   的信息吗？这个本质和qm_uu_rpc中的trailer信息没有区别。如果是这样，我们直接
   key-value这种格式，直接定义一个二进制结构，把需要承载的数据直接编码进去，不
   是更符合二进制共享内存的形式？何必反过来去学http那种非要编码成文本的结构呢？
   你说对吗？

下面这个是它的回答：::

   你说得对。我反思一下我刚才那段话——我又犯了一次同样的错误：从"外部有什么参考
   "出发，而不是从"我们是什么、需要什么"出发。

   你刚才点破的，正是我第一轮 metadata 建模犯的错的同一根源：

   - gRPC 把 metadata 编码成文本 key-value，是因为 HTTP 本来就是文本协议，它复
     用了已有能力。
   - 我看到"gRPC 有 metadata"，就直接抄过来，把"它为什么这么做"忘了。
   - 然后我刚才还更进一步——既然我们要"长远的可扩展设计"，我就建议去学 DHCP/TLV
     那种成熟模型。但那些是为变长、类型多样、跨网络异构设备设计的。

   我们的实际形态是：二进制共享内存 RPC。caller 和 callee 两端是同一份 mmap 的
   内存，两端就是 C 结构体直接读写。我刚才建议的 TLV/类型注册表那一套，在这个
   形态下是纯负担——没有跨设备编解码、没有异构序列化问题、不需要自描述。

还有这个：::

   我觉得你的设计目标还是不干净，把很多“设计结果”放到目的里面去了，我改写了一
   次，请你看看是否同意我这个总结，如果同意，请按这个目标来建立后续逻辑。 你原
   来的目标包含太多设计结果了，比如我们要支持metadata编码，是因为里面有功能我
   们也需要（比如trace id形式的调试），不是因为gRPC有这些属性，所以我们也要编
   码这些属性。又比如我们要扩展StatusCode，因为我们的gqm通讯有自己特有的错误类
   型，需要能分辨，而不是因为gRPC有这些错误类型，我们也得加上，对不对？ 

这是它的答复：::

   读完了你的改写。我完全同意你阐述的原则——这是个真实的方法论错误，我的版本里"
   目的"和"设计结果"混在一起，等于用 gRPC 的功能清单反推需求。但我想诚实地给你
   一个判断：你的改写比我的版本好很多，可它还残留着"gRPC 打头"的框架，没有完全
   贯彻你自己在消息里讲的原则。具体看：

   你的原则（你消息里的表述，need-first）

   - metadata：因为里面有功能我们也需要（比如 trace-id 形式的调试）
   - StatusCode：因为我们的 gqm 通讯有自己特有的错误类型，需要能分辨

   主语都是"我们的需要"。

老实说，我很想把这些原则写成Skill，但我真不知道可以怎么写。
