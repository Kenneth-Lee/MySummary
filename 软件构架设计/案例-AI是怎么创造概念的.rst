案例-AI是怎么创造概念的
***********************

这个文档是一个\ :doc:`案例-有构架地解决问题`\ 之外的独立案例，因为是一个独立方
向问题，我单独写出来了。

下面是我给AI提的一个意见：::

  我看了你这个实现，我觉得这个设计修改，本质是调整caller状态机，增加一种刺激
  （abandon），要修改就从状态机调整开始，要穷举这个刺激对每个状态的影响，判断
  是否需要增加状态。我根据这个策略更新了qm_uu_rpc.md的状态机定义，请你看是否同
  意这个建模。

这是AI的答复：::

  我读完了你的状态机建模，先说结论：我同意你的 Cancelled 状态建模，我之前的
  "abandoned 标记法"是错的方向。

  我之前做的是"标记法"：在 caller_rt 加 abandoned bool，在 CALL_DONE 正常路径
  里偷插一个 if (caller->rt.abandoned) 分支丢弃 payload 回 Idle。这是在状态机
  里开后门，破坏了状态机的清晰性——状态还是 WaitRsp，但行为变了，合法性检查也乱
  了。

  你的"状态法"对在哪：

  1. 独立状态 Cancelled 是正交的建模。放弃是一个新的激励，它把 caller 推进一个
       明确的状态，而不是给某个状态偷偷改行为。状态机的合法事件检查保持清晰。
 
  2. 收到对端消息 → 发 ERROR → Idle 比"静默丢弃"正确。我之前的设计决定（对话历
       史里"不发新 wire 消息，对端响应到达被丢弃"）是错的。因为对端如果在
       Sending（发超长响应的后续 chunk），会持续发 MORE，caller 不通知的话一直
       丢弃，浪费带宽 + CPU。发 ERROR 让对端立即复位到 Idle，是和ERROR 原有语
       义（"要求对端复位"）一致的、对称的做法。
 
  3. 利用"对端消息到达"作为发 ERROR 的同步点是正确的时序。放弃时不能立即发
       ERROR——因为此时 caller 的 block 还对齐着"等响应"的布局，贸然写ERROR 会
       和对端路上在途的响应交错。等对端消息被 poll 取出（block 被对端写过一轮
       了），此时发 ERROR 时序安全。

我收集这个案例不是说明AI会犯什么错误，而是讨论它发明“新概念”的能力。它这里的
“标记法”和“状态法”这个名字起得是真的好，因为在这个上下文中，这两个名字确实总结
了我们的关键差别。但如果是我写文档，我是不会这样起名字的，因为这些名字放在一个
更大的上下文中，很难解释它是什么意思，但就我们现在这个详细的上下文中，它确实非
常准确。这个例子说明了：为什么很多AI的错判都来自“忘掉历史”，即使这个历史就在上
下文中，因为作为概率模型，它确实就是尝试不断在最近的上下文中，把“以前”的注意力
综合成一个范围有限的“新名字”，这个新名字只在那个上下文区域中有语义，到了新的上
下文区域中，就变成幻觉了。
